Run-statistics overhead benchmark

Benchmark reports and raw evidence live in this documentation directory. The runnable benchmark scripts remain in python/benchmarks/; reproduction commands below run from the repository's python/ directory.

Bounding-box partitioning

The bounding-box reference describes the implementation and geometry comparison using external annotation inputs. The earlier reduced-workload runtime report has been withdrawn; it did not establish performance on the complete recorded paths. Full-path runtime comparisons use the original source datasets and retain raw evidence outside the repository.

Historical native reference measurements and metric semantics (#139)

The historical native real-data evidence measures revision 10145cd, using manager-owned shared-buffer observations. It does not measure the removed worker/TIFF registry or Windows working-set enumeration. Later review cleanup removes formatting-only pipeline changes; these recorded runs are still explicitly at 10145cd, not a new benchmark of the later revision.

The Windows test runtime uses the disclosed CloudFiles zero-width-interval patch with dependency provenance. CloudFiles 5.8.2 rejects transfers whose start/end timestamps coincide at the Windows Python 3.11 clock resolution; the isolated workaround represents such intervals as one microsecond. It is identical for off/on treatments and changes only the temporary test dependency, not a shipped dependency.

Method and timing boundary

The original PosteriorSalivaryDuct_cut_ng.json supplies the PSU Octo9 16-bit image layer at mip 0. Each run uses 120 × 120 uint16 slices, adaptive spacing 1 / ratio 0.5, 128 target slices per box, 12 workers, and one BLAS/OpenMP thread. Short 2 (Posterior Salivary Duct 2) has 10 annotation points / 875 slices; Short 3 (Posterior Salivary Duct 3) has 16 points / 887 slices; Long (Posterior Salivary Duct) has 50 points / 4,901 slices. Each treatment backprojects its own sliced intensity TIFF, with 160³ chunks, zlib, minimum bounding box and separate output planes; the data is not binarized.

Linux/WSL2 (Python 3.11.13) and native Windows (Python 3.11.9, build 22631) ran sequentially on the same shared development host. Each path received one disabled slicing warmup, then two pairs: off → on, then on → off. Caches were shared; remote metadata requests can remain. On enables reporting and RAM collection together through --verbose; off omits both. No pixels were hashed. All 48 measured operations succeeded, all 24 enabled operations returned non-null memory peaks, and all six excluded warmups succeeded. No attempts were selected out.

Overhead uses the existing SliceParallelPipelineStep or BackprojectPipelineStep duration. It includes data downloads, computation, output writes, intermediate cleanup, and worker/manager startup and shutdown inside that step. Earlier parsing, geometry and source/cache setup, sampler startup/shutdown, and final report formatting/writing/delivery are excluded. The separate Pipeline.process() timer is retained in the raw files. RAM collection covers that broader pipeline window, so collector CPU/sweep costs must not be divided by the shorter data-step duration and called overhead.

Owner-approved acceptance scope

The owner limited the combined 1% in-operation engineering target to longer runs, assessed alongside inter-run variability and fixed startup/shutdown costs. For this evidence, acceptance is scoped to the measured Long path; no general minimum-duration threshold or blanket short-operation guarantee is established. Startup/shutdown outside the data step remains excluded. Fixed lifecycle work inside the step can be significant for short runs, but these measurements do not isolate it or establish that it explains every positive difference.

Long-path median changes were −1.764% slicing / −6.737% backprojection on Linux, and −7.260% / +0.288% on Windows. Windows long backprojection's +0.208 s difference is below both MADs (1.806 s off / 0.769 s on) and changes sign between pairs. These results satisfy the owner-approved engineering assessment for the measured long workloads; two pairs on a shared host do not prove a statistical 1% upper bound. Negative changes indicate measurement variation, not an instrumentation-induced speedup.

Short-run costs remain findings: Linux Short 2 slicing/backprojection and Short 3 slicing were slower in both pairs, with differences exceeding both treatment MADs; Windows Short 3 slicing has the same pattern. These observations are accepted outside the scoped target, not recast as negligible overhead. Native macOS pipeline performance and macOS-host Docker delivery are explicitly deferred; native unit-test CI is not a substitute for those workflow runs.

Memory coverage limits

One-second sampling can miss brief peaks or short-lived children. Segments released by, or allocated outside, SharedNPManager can be missed while still attached elsewhere. A deliberately retained-buffer fixture demonstrated a 32 MiB omission, but real-data probes after #147's worker-startup fix attributed the large observed gaps to TIFF backing, not persistent retained shared buffers. Normal pipeline allocations use the manager; this does not prove retention impossible.

The collector does not separately count resident TIFF/file cache after its process mappings disappear. Earlier sparse Linux diagnostics observed additional TIFF residency of 262–263 MiB slicing / 95.05 MiB backprojection for long Salivary, and 240–256 MiB / 35.12 MiB for corrected Daphnia. These are diagnostic observations, not peak-error bounds or Windows accuracy measurements. Ouroboros controls file writes/closure, but cache retention and eviction are OS-controlled.

Linux PSS includes other mapped/shared pages proportionally. Windows excludes other shared pages and counts managed allocated, rather than resident, bytes; untouched or paged-out managed memory can therefore be overcounted. Do not interpret the difference between Windows and Linux peaks as an actual physical-RAM difference.

Reproducing the benchmark

From python/, with the project's virtual environment installed, reuse saved slice/backprojection options and choose a new work directory:

.venv/bin/python benchmarks/benchmark_run_statistics.py \
  --real-slice-options /path/to/slice-options.json \
  --real-backproject-options /path/to/backproject-options.json \
  --work-dir /tmp/ouroboros-real-data --workers 12 --pairs 2 --timeout 3600

This copies original annotations, preserves the image source/scientific settings, and visits every annotation path from shortest list to longest. Use --annotation-layer "Exact path name" to select a path without editing the annotations; repeat the option for multiple paths. Selection is recorded and checked when resuming. Both timing boundaries above are recorded without adding production timers. Each pair runs slicing then backprojection of that exact output. Output headers, times, logs, options and reports remain; scientific TIFFs are removed after matching backprojection succeeds. No pixel hashing is performed.

Failed trials remain recorded and dependent backprojections are marked skipped; remaining independent trials still run. A missing usable RAM sample is retained as a coverage failure, not silently treated as a disabled collector. An incomplete pair receives no aggregate overhead estimate. --resume-real-data completes an interrupted batch without repeating completed/failed attempts, after checking production code, annotations, settings and dependency versions. Retain all results; do not retry/select favorable trials or enlarge a workload merely to conceal costs. --workers must be a multiple of four. Sandbox execution must permit the existing multiprocessing manager sockets.

Other harness modes

These modes remain useful diagnostics; their timing boundary differs from the real-data acceptance comparison. Neither substitutes for Docker report delivery.

# Existing local fixture; time Pipeline.process(), including preparation.
.venv/bin/python benchmarks/benchmark_run_statistics.py \
  --scope pipeline --reuse-fixture /tmp/ouroboros-statistics-final \
  --work-dir /tmp/ouroboros-pipeline-overhead --pairs 3

# Generate a local fixture and time the full CLI handler.
.venv/bin/python benchmarks/benchmark_run_statistics.py \
  --work-dir /tmp/ouroboros-statistics-benchmark --pairs 7

The default deterministic seed-138 fixture is a 384³ uint16 precomputed volume with 64³ raw chunks / 1 µm isotropic voxels. A curved 32-point path yields 192² slices at 0.5-voxel spacing, with 32 target slices per box. A thresholded warmup segmentation is reused for binary backprojection using 64³ chunks/zlib. Both modes use four workers and one BLAS/OpenMP thread. --size 128 --pairs 3 gives a short smoke check; --timeout bounds each child operation (default 600 seconds).

Pipeline mode externally times the same Pipeline.process() call in both treatments, with one disabled warmup per operation and alternating pair order. It excludes options loading, report collection/delivery and sampler startup/ shutdown; it includes scientific preparation, worker timing aggregation, RAM collection, output writing and pool shutdown. Reused fixtures are not regenerated or pixel-hashed (pixel_equivalence: null).

Full-handler mode includes option loading, pipeline setup/execution/cleanup, report formatting, stdout flush and statistics delivery. Imports/process startup are excluded from that timer and recorded separately. Each operation receives both disabled/enabled warmups and alternating measured pairs. Source creation, segmentation preparation, inspection and removal are outside the measured interval; no remote source is accessed. It hashes output pixels and requires equivalence, checks successful enabled statistics against stdout and absence of disabled sidecars, and fails on missing usable memory samples. Per-run images are removed after inspection. Source/harness digests, hardware, versions, TIFF dimensions, pixel/storage sizes, every individual time and statistical summaries are retained.

Accepted #138 pipeline-only measurement

The pipeline-only result was refreshed after removing the per-clock switches and worker reporting arguments. Both treatments retain the pre-existing worker clocks; the existing PipelineStep methods control accumulation. The run reused the same 384³ local source and segmentation with four workers and one BLAS/OpenMP thread, using three alternating pairs per operation after one disabled warmup. No data was regenerated or pixel-hashed. Production code remained unchanged throughout that test. Its source digest identifies the #138 timing-only implementation, not the current RAM collector.

Operation Disabled median Enabled median Difference Observed overhead MAD, disabled / enabled
Slicing 16.893485 s 16.726067 s -167.418 ms -0.991% 401.156 / 155.981 ms
Backprojection 9.516044 s 9.521981 s +5.937 ms +0.062% 105.412 / 96.389 ms

Backprojection's +5.937 ms difference (+0.062%) is much smaller than its enabled-run MAD of 96.389 ms; slicing's difference is negative. These results remain consistent with negligible in-operation overhead at this measurement resolution. A negative difference is measurement variation, not a speedup claim, and three pairs do not prove a strict statistical upper bound. All samples are retained; no further runs were selected to improve the result.

The development Electron preview was using CPU rendering during this run (a process snapshot showed about 149% CPU). Background activity was not controlled, so absolute runtimes should not be compared with the earlier session, and this is not an idle-machine microbenchmark. The within-run enabled/disabled comparison and its variability are reported together.

Earlier full-handler artifacts and summaries were removed because they measured superseded implementations. The original accepted pipeline measurement and those older artifacts remain in Git history; #138 links its original acceptance numbers directly to that revision rather than to this refreshed file.
