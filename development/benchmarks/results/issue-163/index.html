RAM collector cost and coverage after #162

This campaign measures merged production revision e81c4d4 for #163. Production code, the one-second sampling interval, metric semantics, and report reduction are unchanged. This is engineering evidence; it does not replace publication Table 1 measurements tracked by ouroboros_pub#121.

Findings and remaining work

The identity-growth regression is absent in the controlled probe; blanket negligible-overhead and adequate-peak-coverage claims are not established. All 64 controlled-clock sweeps retain exactly 51 unique processes, with no failures and early/late median sweep costs of 16.500 / 16.808 ms. New successful timed reports have maximum counts of 7/6 for the four-worker fixture and at most 15/14 for 12-worker real-data slicing/backprojection. See the separate identity evidence and its limits below.

The owner-approved 1% engineering target remains limited to #139's named longer Salivary workload, interpreted with variability. In the valid Docker cohort, Long slicing changes by +0.157% (+0.020 s), below both MADs and with opposite pair signs. Long backprojection changes by +6.476% (+0.957 s), above both MADs (0.364 / 0.565 s), with positive changes in both pairs (+0.183% / +13.087%). The latter is a material observed difference and does not establish the scoped 1% acceptance. Two shared-host pairs do not isolate the collector as the sole cause or establish a statistical upper bound. Historical native Linux/Windows acceptance remains specifically at the older recorded revision/deployments.

Nerve changes by −15.345% slicing / −8.219% backprojection. Disabled-treatment MADs are 5.577 / 24.131 s, and the final disabled trial is substantially slower than the first. These measurements illustrate inter-run variation, not a reporting speedup, and do not override the Salivary finding. Fixed-local slicing (+5.198%) and Short 3 slicing (+3.053%) are slower in both pairs with median differences above both treatment MADs. Preserve those short-run costs outside the scoped longer-run target; do not call them negligible. Short 2's failed warmup further limits its timing interpretation.

Long Salivary slicing accepts only 3/13 and 7/14 attempted sweeps; Nerve slicing accepts 8/29 and 16/28. Across these four runs, the 50 incomplete sweeps comprise 29 FileNotFoundError, 19 OSError, and two NoSuchProcess records. Their retained examples name missing /psm_* segments, changed manager observations, and process exits, respectively; none names process-tree churn. Errors are counted by exception class, with only the first message retained per class in each report. These examples point to managed shared-memory allocation and release racing the sweep as the main remaining long-slicing coverage limitation, between the manager manifest read and segment-open or residency checks; individual lifecycle sequences were not traced. The campaign's only two retained Process tree changed during memory sweep examples are both in Short 2 backprojection, consistent with removal of the clock-induced false churn in #162.

Short 3 slicing accepts only one sample, with a maximum of two processes, in each enabled run: its non-null peaks do not establish worker-phase coverage. Nerve backprojection accepts 150/150 and 177/177 sweeps, with maximum sweeps of 437 / 503 ms and collector CPU of 15.522 / 24.066 s across 149.802 / 176.684 s windows. These CPU figures describe observer work, not workload slowdown.

The original failing Nerve report had 1,551 reported processes, a maximum sweep of 18.951 s, 1,132.140 collector CPU-seconds over 1,129.921 s, and 173 complete / 117 incomplete samples. The current counts and sweep costs corroborate removal of duplicate accounting, but these are 12-worker versus 48-worker slicing runs with different durations/hardware. Real slicing's incomplete fraction did not uniformly improve. No historical values are numerically repaired or replaced by this comparison, and the controlled-clock result does not imply that real allocation churn can no longer invalidate a sweep.

#163 remains open for follow-up on the observed Long backprojection cost and an explicit assessment of managed-segment churn and the reported coverage limits before broad overhead or peak-coverage claims. That follow-up must distinguish treatment cost from host variation and retain the same timing boundary; this campaign makes no sampler, interval, metric or scientific-workload changes to obtain acceptance. The cache contents were repaired for testing; the code path that created the bad entries has not been identified or fixed. Native macOS performance and macOS-host Docker delivery remain deferred under #139.

Deployment and timing protocol

The CLI harness ran in an isolated Linux Docker container on Windows 11 Enterprise 22631 / WSL2, with an Intel Xeon W-10855M (6 cores, 12 logical CPUs). Docker Desktop's Linux VM exposed 12 CPUs and 70.67 GiB RAM; the container had no extra CPU/memory cap and a 64 GiB /dev/shm. Python was 3.11.12, psutil 7.1.3, NumPy 1.26.4, SciPy 1.11.2, tifffile 2024.12.12, CloudVolume 12.7.0 and CloudFiles 5.8.2. All installed versions represented in poetry.lock match it. CloudVolume's metadata says 12.7.0, but its recorded wheel origin and hash match the declared 12.7.0a0 fork. BLAS/OpenMP/MKL threads were limited to one in both treatments. Existing application containers remained running on this shared development host.

The local image ID is sha256:3719d0a81c31dd078d78fed6398c6d2441a2e918fb7db4d6ca7771c3b5ce1ea2. It retains the installed dependency environment from local image sha256:44f155af7e0ff1971ccce2a70760da78472238984643a8cc442ba561bce8d37d and copies the exact fixed production source over it. Neither image has a registry RepoDigest. This was not a fresh release-image certification. See provenance, the campaign Dockerfile, and the container provenance reader.

Reporting off omits --verbose; reporting on enables statistics and RAM collection together. Each workload has two pairs in order off → on, then on → off. Summaries use the existing benchmark summary() function, including per-treatment MAD. Overhead uses the existing data-step duration: downloads, computation, writes, worker/manager lifecycle and cleanup inside the step all count. Earlier parsing/geometry/source setup, sampler startup/shutdown outside the step, and final formatting/persistence/delivery do not. The external Pipeline.process() timer is reported separately. Observer CPU time spans the broader sampling window and is not additive elapsed-time overhead.

Workloads retain the existing scientific configurations:

  • Fixed local: seed 138, 384³ uint16 source, 192 × 192 slices, four workers, one disabled warmup per operation, the existing pipeline benchmark mode.
  • Salivary: the original three PosteriorSalivaryDuct_cut_ng.json paths, 120 × 120 uint16 slices, adaptive distance 1 / ratio 0.5, 128 target slices per box, 12 workers. Short 2 has 10 points / 875 slices; Short 3 has 16 / 887; Long has 50 / 4,901. Each treatment backprojects its own intensity TIFF with 160³ chunks, zlib, minimum bounding box and separate output planes.
  • Nerve: Long Nerve Trace from NerveCords_ng.json, 59 points / 10,386 uint16 slices of 120 × 120, the saved source/scientific options and the same 12-worker treatment protocol. Each treatment backprojects its own sliced intensity TIFF, as for Salivary. Explicit annotation selection leaves the original annotation file unchanged.

Real-data paths use one disabled slicing warmup, a shared CloudVolume cache and uncleared OS caches; remote metadata requests may remain. No timed trial hashes output pixels. Every attempt, including failed warmups and dependent skips, remains in the raw results. The original failure used 48 workers; this 12-CPU, 12-worker campaign is corroborative, not a matched reproduction of that deployment. No new native Windows/macOS or GUI/server delivery run was performed. Historical native Linux/Windows comparisons and macOS workflow deferrals remain in the parent benchmark report.

Source-cache failure and separate recovery cohort

The original Salivary Short 2 warmup failed with HTTP 416, although all 16 measured operations for the two short paths completed. That failed warmup means Short 2 does not establish the intended warm-cache condition. The original Long warmup and all four measured slices failed gzip decoding; their four backprojections were skipped. They have no overhead estimate.

The benchmark cache was repaired; the code path that created the bad entries has not been identified or fixed.

An offset is a byte position inside a file. This dataset is stored in large shard files, each with index blocks locating its contents. Forensic evidence identifies two bad cached 11b.shard-*.msi files. Their bytes exactly match remote shard 11b read at positions specified by shard 152's index. Reading 11b at its correct positions returns valid indexes, and a fresh metadata-only CloudVolume reader succeeds. All six other cached MSI entries pass gzip and expected-length checks. This establishes a file/offset mismatch in the cached data; the originating code path remains unproven. No race or other specific originating cause is established.

CloudVolume saved the incorrect bytes before checking whether they could be decompressed. Subsequent attempts reused them and repeatedly failed with the same gzip error, before the malformed indexes could supply image-chunk offsets. This specific failure does not establish a general proof of image-data integrity.

The original cache and failed cohort were preserved. A separate cache copy replaced exactly those two entries with the validated remote bytes, recorded in cache recovery provenance. The separately named salivary-long-validated cohort gets a full new disabled warmup and both complete pairs. Its results are not pooled with the failed original cohort. Nerve follows using that cache. No production code, dependency, source volume, or annotation was patched to obtain these results.

"Cold-cache" describes the circumstances in which the bad entries were encountered; it does not establish that an empty cache alone triggers the failure. Because the originating code path remains unresolved, the problem could recur when uncached indexes are downloaded. This is a data-loading/cache finding discovered during the RAM campaign; there is no evidence that RAM collection caused it.

The native identity checks passed 26 tests inside the measured image. The first test invocation emitted a pytest cache-permission warning because UID 1000 could not write /app/.pytest_cache; rerunning with -p no:cacheprovider passed without warnings. Both invocation outcomes are retained in provenance. This is not another implementation of #162's platform-contract tests.

The controlled-clock probe uses production TreeSampler to observe a separate root and 50 waiting children. It changes only psutil's boot-time conversion, including a shift after the first native memory read, while the OS clock remains untouched. Canonical psutil.Process identities and export_process_identity supply the evidence; no PID/timestamp identity algorithm is reimplemented. The observer and its growing JSON ledger live outside the measured tree, and evidence serialization is outside the timed sweep. The probe demonstrates repeated rediscovery under injected clock movement, not long-workload overhead or managed buffer coverage. Timed operation reports retain aggregate counts, not per-sweep PID traces; the merged production unique-PID guard and separate identity probe are the corresponding uniqueness evidence.

The new --annotation-layer option only selects which existing annotation layers the benchmark schedules. It preserves input bytes and records/checks selection on resume. The existing pipeline timers own operation durations, RunStatistics and MemoryCollector own lifecycle/reporting, TreeSampler owns process discovery and RAM reads, and the existing benchmark summary() owns the timing reduction. No duplicate production writer, carrier, calculation or sampler was added or removed. Exported identities, JSON reports and tables are read-only evidence adapters, not another runtime authority.

Postflight verified unchanged production source, dependency resolution and harness fingerprints, and an empty /dev/shm. Across all cohorts, 40 measured operations succeeded, four measured slices failed and four dependent backprojections were skipped. Five of seven excluded warmups succeeded; both failed warmups remain.
